## 2. Модули и зависимости

Три части, зависимости идут строго в одну сторону:

```
physics  ◄──  main  ◄──  client
(чистая Java)  (общий код мода)  (только клиент)
```

| Часть | Где лежит | От чего зависит | Что внутри |
|---|---|---|---|
| `physics` | отдельный подпроект Gradle `physics/` | только JDK | Математика движения и взрыва в единицах TF2 |
| `main` | `src/main` | `physics`, Minecraft, Fabric API | Mixin движения, классы, оружие, сущности, сеть, конфиг, команды |
| `client` | `src/client` | `main` | Ввод, HUD, рендер, приём пакетов |

`physics` вынесен в подпроект, а не в пакет внутри `main`, чтобы правило «без зависимостей от Minecraft» обеспечивала сборка: класс Minecraft там просто не скомпилируется. Побочный плюс: его тесты запускаются за секунды и не требуют загрузки игры.

Классы подпроекта кладутся прямо в jar мода, отдельным файлом он не поставляется. Задача `verifyJarContents` при каждой сборке проверяет, что в jar есть и мод, и `SourceMovement`.

## 4. Граница единиц

- Внутри `physics` всё в единицах TF2: u, u/s, u/s², секунды.
- Minecraft хранит скорость в блоках за тик.
- Пересчёт делается в одном месте, в `movement/` (мост): `блоки/тик = u/s ÷ масштаб ÷ 20`.
- Масштаб (45 u/блок) берётся из конфига. Ни в `physics`, ни в остальном коде число 45 не встречается.

## 5. Движение

Раздел подтверждён чтением декомпилированного кода Minecraft 26.3 (2026-10-11). Имена классов и методов ниже — из этого кода.

### Кто считает движение

Позицию своего игрока определяет клиент. Сервер каждый тик делает три вещи:

1. Выполняет обычный тик игрока, включая `travel`, а затем возвращает игрока в последнюю принятую позицию (`ServerGamePacketListenerImpl.tickPlayer`). То есть серверный расчёт движения выполняется, но его результат по позиции отбрасывается. Скорость (`deltaMovement`) на сервере при этом остаётся.
2. Принимает позицию из пакета клиента и проверяет её (`handleMovePlayer`).
3. Рассылает позицию остальным игрокам.

Проверки сервера:

| Проверка | Условие срабатывания | Что это значит для мода |
|---|---|---|
| «moved too quickly» | Квадрат смещения за пакет превышает квадрат серверной скорости больше чем на 100, то есть около 10 блоков за тик | Не мешает: потолок TF2 3500 u/s — это 3,9 блока за тик |
| «moved wrongly» | Сервер повторяет перемещение со своими столкновениями и получает расхождение с клиентом больше 0,25 блока | Проверяются столкновения, а не физика. Не мешает, пока клиент перемещается штатным `move` |
| Кик за полёт | Игрок висит в воздухе, не снижаясь, дольше допустимого числа тиков | Долгий подъём от взрыва короче этого порога, но проверить на прототипе |

Первые две проверки не действуют на владельца одиночной игры и отключаются игровым правилом. После внешнего импульса проверку «moved wrongly» можно временно ослабить штатным методом `applyPostImpulseGraceTime`.

Следствие для проекта: формулировка «один и тот же код на клиенте и сервере» означает не повторный расчёт движения на сервере, а три вещи:

1. Мод установлен на обеих сторонах, и серверные проверки не отбрасывают скорости TF2.
2. Параметры движения задаёт сервер и рассылает клиентам, клиент свои значения не использует.
3. Всё, что меняет скорость извне (взрыв), считает сервер и отправляет клиенту.

Сервер при этом доверяет клиенту в том, как тот движется. Защита от читов в scope не входит.

### Как устроено ванильное движение

`Player.travel(Vec3)` вызывает `LivingEntity.travel`, а тот выбирает одну из трёх веток: `travelInFluid` (вода и лава), `travelFallFlying` (элитры) или `travelInAir`. Название последней обманчиво: это и ходьба по земле, и полёт в прыжке. В ней игра прибавляет ускорение от ввода, перемещает игрока с учётом столкновений, вычитает гравитацию и умножает скорость на трение.

Гравитация и сила прыжка в 26.3 — атрибуты сущности (`GRAVITY`, `JUMP_STRENGTH`). Прыжок выполняет `LivingEntity.jumpFromGround()`: задаёт вертикальную скорость и при беге добавляет толчок вперёд.

### Точка встраивания

Mixin встраивается в начало `LivingEntity.travelInAir` и срабатывает только для игрока. Отличие от прочитанных модов: оба перехватывают `Player.travel` целиком и потом сами разбирают, вода это, элитры или полёт. Перехват `travelInAir` получает эти случаи бесплатно: в воде, лаве и на элитрах игра туда просто не заходит, и там остаётся ваниль.

Движение TF2 считается только для локального игрока на клиенте. `Tf2Travel` решает, применяется ли движение TF2, и принимает прыжок; сам тик считает `SubstepLoop`, который работает с игроком через интерфейс `MovingBody` (скорость, перемещение со столкновениями, опора, взгляд) и не использует классы игры. Поэтому цикл подшагов покрыт юнит-тестами с подставным игроком, а `Tf2Travel` только передаёт вызовы штатным методам игрока. На сервере метод тоже вызывается, но его результат по позиции отбрасывается, поэтому там остаётся ванильный расчёт. Проверено в T1.3 клиентским игровым тестом на выделенном сервере: позиции клиента и сервера совпадают, сообщений о неверном движении нет.

Три детали реализации, найденные на практике:

- **Поправка ввода.** Игра умножает ввод игрока на 0,98 до расчёта движения; мост делит на 0,98 обратно, иначе полное нажатие давало бы 98% скорости.
- **Прижатие к земле.** Игрок, стоящий на земле, каждый шаг смещается вниз на величину, близкую к ванильной гравитации за тик. Без движения вниз игра не видит опоры под ногами и считает игрока висящим в воздухе.
- **Столкновения на каждом подшаге.** Перемещение вызывается для каждого подшага отдельно, скорость перед ним записывается в поле игрока: при столкновении игра сама обнуляет нужную составляющую.
- **Плавный поворот взгляда.** Игра обновляет взгляд раз в тик, а свой прошлый угол к моменту расчёта движения уже приравнивает к текущему. Мост запоминает угол прошлого тика сам, и подшаги считаются с углами между прошлым и текущим.
- **Замедляющие блоки раз за тик.** Игра умножает скорость на замедление блока при каждом перемещении. На промежуточных подшагах цикл берёт скорость до перемещения, если игрок ни во что не упёрся.
- **Новое нажатие на каждый прыжок.** `JumpGate` следит за клавишей прыжка и пропускает прыжок, только если её зажали заново не раньше чем за два тика до приземления.

До шага 8 классов нет, поэтому движение включается временной командой `/tf2 movement on` и считается с максимальной скоростью 300 u/s.

Порядок внутри перехвата:

1. Проверить, применимо ли движение TF2. Если нет — ничего не делать, работает ваниль.
2. Собрать `MoveInput` и `MoveState`, пересчитать в единицы TF2.
3. Вызвать `SourceMovement` (один раз или по подшагам).
4. Пересчитать скорость обратно и передать её штатному `move(MoverType.SELF, ...)`, чтобы столкновения с блоками и подъём на ступеньки остались ванильными.
5. Отменить ванильный расчёт: трение, ускорение и гравитацию.

Движение TF2 не применяется, и остаётся ваниль: на лестницах и лианах, в творческом полёте и режиме наблюдателя, верхом, а также если у игрока не выбран класс TF2.

### Известные ограничения

Найдены аудитом 2026-10-11. Это не ошибки, а места, где движение TF2 пока игнорирует механики Minecraft или проверено слабее остального.

| Что | Как сейчас | Когда разбираться |
|---|---|---|
| Скользкие блоки (лёд, слизь) | Трение блока под ногами не учитывается: лёд не скользит | после вехи |
| Замедляющие блоки (песок душ, мёд) | Замедление действует раз за тик, как в ванили | — |
| Эффекты Скорость, Прыгучесть, Плавное падение | Не действуют, пока включено движение TF2 | вместе с правилами класса, шаг 8 |
| Бег (клавиша спринта) | На скорость не влияет, но поле зрения по-прежнему расширяется | шаг 8 |
| Ступеньки, стены, потолки, края блоков | Работают через штатное перемещение игры; проверено клиентским тестом на полублоке, блоке, стене, потолке и краю площадки | — |
| Скольжение вдоль стены под углом | Не быстрее максимума класса: на земле скорость обрезается, как в TF2. Замер: 298 u/s при максимуме 300 | — |
| Прыжок на мелководье | Ванильный прыжок со скоростью прыжка TF2: высота 46,5 u при 52 u на суше, разницу съедает вода | — |
| Вода, лава, элитры | Остаётся ваниль; проверено чтением кода, игровых тестов на глубокую воду, лаву и элитры нет. Лестница проверена клиентским тестом | после вехи |
| Прыжок при удержании клавиши | Один прыжок на нажатие, как в TF2, с запасом 2 тика до приземления. Ванильный автопрыжок при включённом движении TF2 не работает | запас — при оценке ощущений |
| Проверка в CI | Цикл подшагов (`SubstepLoop`) покрыт юнит-тестами в CI. Миксины и тонкая обёртка над игроком в `Tf2Travel` по-прежнему проверяются только клиентским игровым тестом, который в CI не работает | T1.7, до вехи |
| Команда `/tf2 movement` | Доступна любому игроку и даёт скорость 300 u/s | исчезнет на шаге 8 |

### Прыжок

Высота прыжка задаётся параметром и подбирается под 50 u (см. `05-sources.md`). Перехват — в `LivingEntity.jumpFromGround()`: подставляется скорость прыжка TF2 и убирается ванильный толчок вперёд при беге. Сервер тоже вызывает этот метод, когда видит по пакету клиента, что игрок оторвался от земли.

Ванильная задержка между прыжками при удержании клавиши мешает распрыжке. goldsqource убирает её, обнуляя `noJumpDelay` в `aiStep()`. Открытый вопрос T1.3: в TF2 удержание прыжка не даёт прыгать непрерывно, на каждый прыжок нужно новое нажатие. Повторять ли это поведение или разрешить прыжок по удержанию, решается на прототипе.

### Подшаги

`SourceMovement` принимает шаг времени параметром, поэтому три подшага по 1/60 с и один шаг 0,05 с — это один и тот же код с разными аргументами. Открытый вопрос T1.4: проверять столкновения на каждом подшаге или один раз за тик.

Первые числа для этого выбора дал юнит-тест `airStrafeGainDependsOnStepLength`. Идеальный стрейф Soldier в течение секунды с начальной скорости 240 u/s даёт:

| Шаг расчёта | Скорость через секунду |
|---|---|
| 0,015 с — тик TF2 | 343 u/s |
| 1/60 с — три подшага за тик Minecraft | 334 u/s |
| 0,05 с — один шаг за тик Minecraft | 275 u/s |

Причина: прибавка скорости за один шаг ограничена потолком 30 u/s, поэтому важна не длина шага, а число шагов в секунду. Один шаг за тик заметно ослабляет стрейф, три подшага почти совпадают с TF2. Прыжок и разгон на земле от длины шага не зависят.

goldsqource подшаги не использует: один расчёт за тик, но ускорение в воздухе считается так, будто шаг равен 1/100 с. Гравитацию и столкновения он оставляет ванильными. Это вариант для сравнения в T1.4.

## 6. Сеть

Fabric API: запись-пакет реализует `CustomPacketPayload`, регистрируется через `PayloadTypeRegistry`, отправляется через `ServerPlayNetworking` и `ClientPlayNetworking`.

| Пакет | Направление | Когда |
|---|---|---|
| Параметры движения и масштаб | сервер → клиент | при входе игрока и после перечитывания конфига |
| Класс игрока | сервер → клиенты | отдельный пакет не нужен, если класс хранится через Attachment API с синхронизацией (раздел 8) |
| Выстрел | клиент → сервер | при нажатии атаки; сервер проверяет боезапас и интервал |

Скорость от взрыва отдельного пакета не требует. Сервер меняет скорость игрока и выставляет флаг `syncVelocity`; в том же тике игра сама отправляет штатный пакет скорости и самому игроку, и тем, кто его видит (`ServerEntity.sendChanges`). Подтверждено по коду 26.3.

Известный риск: ракетный прыжок в этой схеме срабатывает с задержкой на пинг, потому что импульс приходит с сервера. В TF2 клиент предсказывает свой взрыв. Для прототипа задержка принимается; предсказание на клиенте — возможная доработка после вехи.

## 7. Конфиг

Файл `config/tf2mc.json` в папке игры (в разработке — `run/config/tf2mc.json`). Если файла нет, мод создаёт его при запуске со значениями по умолчанию:

```json
{
  "movement": {
    "accelerate": 10.0,
    "airAccelerate": 10.0,
    "friction": 4.0,
    "stopSpeed": 100.0,
    "gravity": 800.0,
    "airSpeedCap": 30.0,
    "jumpSpeed": 289.0,
    "maxVelocity": 3500.0
  },
  "unitsPerBlock": 45.0,
  "substeps": 3
}
```

Параметры движения — в единицах TF2. `unitsPerBlock` — масштаб, `substeps` — сколько раз за тик считается движение, от 1 до 10.

Правила чтения:

- Пропущенный параметр получает значение по умолчанию.
- Неизвестный параметр не ошибка, но о нём пишется предупреждение: обычно это опечатка.
- Ошибка в файле (не JSON, не число, значение вне границ) не роняет игру и не сбрасывает настройки: остаются прежние значения, причина пишется в лог и в чат.

Команды: `/tf2 config` показывает действующие значения, `/tf2 reload` перечитывает файл (только для операторов).

Чтение через Gson, который уже входит в Minecraft; новая зависимость не нужна. Разбор и проверка значений (`ConfigParser`, `Tf2Config`) не используют классы игры и покрыты юнит-тестами.

На выделенном сервере действует файл сервера. Клиент получает значения пакетом `MovementSyncPayload` при входе, при переключении движения и после `/tf2 reload`, и считает движение по ним, а не по своему файлу.

## 8. Классы TF2

- Описание класса (HP, скорость, набор оружия) — данные, а не код.
- Класс игрока хранится на сервере и должен переживать смерть и перезаход.
- Рекомендуемый способ хранения — Attachment API из Fabric API: `AttachmentRegistry.create` с `persistent(...)`, `copyOnDeath()` и `syncWith(..., AttachmentSyncPredicate.all())`. Это даёт сохранение, перенос через смерть и рассылку клиентам без своего пакета. Открытый вопрос 1 в `04-decisions.md`, ждёт подтверждения перед шагом 8 плана.
- Максимальная скорость класса передаётся в `MoveParams`, а не через ванильный атрибут скорости, потому что ванильное ускорение отключено.

## 9. Данные

`classes.json` и `weapons.json` лежат в ресурсах мода, `src/main/resources/data/tf2mc/`. Игра грузит их как датапак и перечитывает командой `/reload`. Корневой папки `data/` в репозитории нет (решение от 2026-10-11).

Единицы TF2 (u, u/s) хранятся в файлах как есть, пересчёт в блоки делает код через масштаб из конфига. Каждое число сначала получает строку со статусом `сверено` в `05-sources.md`.

## 10. Ракета и взрыв

- Ракета — своя сущность-снаряд. Каждый тик сервер проверяет весь отрезок пути за тик (около 1,2 блока при 1100 u/s) на пересечение с блоками и сущностями.
- Взрыв свой: блоки не разрушает. Урон и отбрасывание считает `ExplosionMath` из `physics`, поэтому формулы покрываются юнит-тестами.
- Эффекты и звук — из ванильных ресурсов Minecraft. Ассеты Valve не используются.

## 11. Тесты

| Уровень | Где | Что проверяет | Состояние |
|---|---|---|---|
| Юнит-тесты мода | `src/test` | Согласованность `fabric.mod.json` с кодом, валидность всех JSON в `src`, разбор и проверка файла настроек, чтение и перечитывание файла, пересчёт единиц и поворот ввода, запись и чтение сетевого пакета, цикл подшагов с подставным игроком (прижатие к земле, поправка ввода, столкновение со стеной, прыжок только на первом подшаге, сход с края) | есть, 58 тестов |
| Юнит-тесты физики | `physics/src/test` | `SourceMovement`: разгон, трение, стрейф в воздухе, прыжок, независимость от длины шага. Без игры, выполняются за доли секунды. `ExplosionMath` появится на шаге 9 | есть, 37 тестов |
| Серверные игровые тесты | `src/gametest` | Сервер с модом стартует; команда `/tf2` зарегистрирована; правка файла и `/tf2 reload` меняют настройки, а ошибочный файл их не сбрасывает. Позже: ракета, взрыв, смена класса | есть, 3 теста; в логе сервера их четыре, потому что игра всегда добавляет свой встроенный `always_pass` |
| Клиентские игровые тесты | `src/gametest` | Настоящий клиент нажимает клавиши и измеряет движение: скорость, остановка, высота прыжка, стрейф, действие настроек сервера, совпадение позиций клиента и сервера. В одиночной игре и на выделенном сервере Плюс восемь сценариев на неровностях: ступенька, блок, стена, потолок, край, мелководье, лестница | есть, один сценарий на оба режима, 30 замеров в каждом |
| Ручная проверка | игра | Ощущения, связка «выделенный сервер + клиент» | по шагам плана |

Юнит-тесты, линтеры и серверные игровые тесты запускаются одной командой `gradlew build`. Только юнит-тесты: `gradlew test`. Только серверные игровые: `gradlew runGameTest`. Клиентские игровые: `gradlew runClientGameTest` — открывается окно игры, прогон занимает около минуты.

Юнит-тесты написаны на обычном JUnit 5 и классы Minecraft не загружают. Если понадобится тестировать код, который трогает классы игры, потребуется `fabric-loader-junit` — это отдельная зависимость, подключается по согласованию.

### Линтеры и проверки кода

| Проверка | Что ловит | Где настроена |
|---|---|---|
| Предупреждения компилятора как ошибки | Сырые типы, небезопасные приведения, устаревшие вызовы и остальное из `-Xlint:all` | `build.gradle`, для всех наборов исходников |
| Checkstyle 14.3.0 | Неиспользуемые импорты и импорты со звёздочкой, пустые блоки, пропущенные скобки и `@Override`, отступы пробелами, пробелы в конце строк | `config/checkstyle/checkstyle.xml` |
| Проверка JSON | Битый JSON в ресурсах мода | тест `ResourceJsonTest` |
| `.editorconfig` | Единые отступы и кодировка в редакторе | корень репозитория |

Из `-Xlint:all` исключены две категории, которые сообщают не о коде мода: `processing` (шум от обработчиков аннотаций) и `classfile` (аннотации внутри чужих jar).

Запуск только проверок без сборки jar: `gradlew check`. Отчёты Checkstyle: `build/reports/checkstyle/`.

Форматирование автоматически не исправляется. Для VS Code нужно расширение «EditorConfig for VS Code», тогда отступы выставляются сами.

Чего нет и когда добавлять: статический анализ (SpotBugs или Error Prone) — когда появится логика движения; автоформатирование (Spotless) — если ручного соблюдения стиля станет недостаточно. Каждое из этих добавлений — новая зависимость, подключается по согласованию.

### CI

`.github/workflows/build.yml` запускается на каждый PR и на каждый коммит в `main`: ставит JDK 25, проверяет подлинность `gradle-wrapper.jar`, выполняет `gradlew build` — то есть все линтеры и тесты из таблиц выше. При падении сохраняет отчёты тестов и Checkstyle и логи тестового сервера, при успехе — собранный jar. Новый коммит в ветку PR отменяет незаконченный прогон по ней; прогоны в `main` не отменяются, каждый коммит получает свой результат.

Клиентские игровые тесты в проверки PR не входят. Для них есть отдельный workflow `client-game-test.yml` с ручным запуском, но на машинах GitHub он пока не работает: без видеокарты клиент Minecraft 26.3 не создаёт окно («Couldn't find matching GLX visual»), установка программного OpenGL и настройка виртуального экрана не помогли. Локально тест проходит, перед PR с изменениями движения его нужно запускать вручную.

## 12. Среда

- VS Code: документация Fabric поддерживает его, но рекомендует IntelliJ IDEA. Для VS Code нужен набор расширений «Extension Pack for Java».
- Запуск из терминала работает в любом редакторе: `gradlew runClient`, `gradlew runServer`, `gradlew test`.
