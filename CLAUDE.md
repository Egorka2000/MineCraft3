# tf2-mc

Fabric-мод: классы Team Fortress 2 со стоковым оружием в Minecraft Java Edition. Приоритет номер один: движение в стиле Source (ракетный прыжок, распрыжка).

## Документы

Читать в начале сессии: `docs/README.md`, затем по необходимости `docs/01-brief.md`, `docs/02-physics.md`, `docs/03-tasks.md`, `docs/04-decisions.md`, `docs/05-sources.md`, `docs/06-references.md`, `docs/07-plan.md`, `docs/08-architecture.md`, `docs/09-commands.md`, `docs/10-mechanics.md`.

## Правила работы

- Брать следующий невыполненный шаг из `docs/07-plan.md`; полный список задач со статусами — в `docs/03-tasks.md`, после выполнения отмечать там `[x]`.
- Принятые решения записывать в `docs/04-decisions.md`.
- Числа TF2 с пометкой **[проверить]** сверять с TF2 Wiki, не угадывать. Результат сверки записывать в `docs/05-sources.md`.
- Математика движения живёт в чистом Java-классе без зависимостей от Minecraft (подпроект `physics`), Mixin только вызывает его. Движение своего игрока считает клиент, сервер его проверяет; параметры движения задаёт сервер и рассылает клиентам. Подробности — `docs/08-architecture.md`, раздел 5.
- Не копировать код Source SDK и ассеты Valve. Алгоритмы переписывать своими словами. Открытый Source SDK 2013 читать только при необходимости и только если нужных сведений нет в других источниках: сначала поиск, потом SDK. В документах указывать, что источником был SDK. Утёкшие исходники TF2 не открывать.
- Одна задача — одна ветка и один PR в `main`. После слияния PR сразу убирать хвосты: удалить рабочую ветку локально и на GitHub, перевести локальный `main` на `origin/main`. Смерженные ветки не копить.
- После каждой крупной волны изменений, не дожидаясь напоминания:
  - закоммитить работу в ветку задачи;
  - обновить документы: статус в `docs/03-tasks.md` и `docs/07-plan.md`, решения в `docs/04-decisions.md`, команды в `docs/09-commands.md`, поведение в игре в `docs/10-mechanics.md`, затронутые разделы остальных документов. Документация должна описывать текущее состояние проекта;
  - проверить и обновить CI, тесты и линтеры: новый код покрыт тестами, новые наборы исходников и подпроекты подключены к Checkstyle и к `gradlew build`, workflow в `.github/workflows` соответствует текущей сборке. Описание в `docs/08-architecture.md` (раздел про тесты и проверки) поддерживать в актуальном состоянии;
  - убрать за собой: временные файлы, логи, остановленные тестовые процессы игры.
- Не захламлять проект. Рабочие и временные файлы создавать только в `tmp/` в корне (папка в `.gitignore`) или в системной временной папке, после использования удалять. Новые папки в корне не заводить без необходимости; если папка нужна, описать её в `docs/README.md`.
- Перед PR прогонять `gradlew build`: он включает проверки компилятора (`-Werror`), Checkstyle, юнит-тесты и серверные игровые тесты. PR вливается только с зелёным CI.
- Если PR меняет движение игрока, сеть или миксины, перед PR дополнительно прогонять `gradlew runClientGameTest`: в CI клиентские тесты пока не работают.
- Новую задачу CI сначала запускать вручную в ветке (`workflow_dispatch`) и включать в проверки PR только после зелёного прогона.
- Решения владельца проекта и код оформлять разными PR.
- Непроверенное объяснение называть гипотезой и в документах, и в отчёте; статус `сверено` ставить только тому, что прочитано в источнике или измерено.
- Проверки не ослаблять ради прохождения сборки: не отключать правила Checkstyle и категории `-Xlint`, не ставить `@SuppressWarnings` без объяснения в комментарии. Если правило мешает по делу, сначала обсудить.
- Версия мода — `version` в `gradle.properties`, она же стоит в имени jar. Вид `0.X.Y`: `X` растёт с каждым PR, который добавляет игроку новое (шаг плана, команда, механика), `Y` при этом сбрасывается в 0; `Y` растёт с каждым PR, который только исправляет ошибку. PR без изменений в игре (документы, тесты, CI) версию не меняют. Новую версию вносить в таблицу в `docs/07-plan.md`.
- Перед изменением версии Minecraft, Fabric или зависимостей спрашивать меня.
- Язык общения и документации: русский.
